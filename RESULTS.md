## Defect report
- Title: Defect 1, excluding all three tools makes `POST /api/pizza` answer 500 with an empty body
- Request: `POST https://quickpizza.grafana.com/api/pizza` with header `Authorization: token <token of a logged-in user>` and body `{"excludedTools": ["Knife", "Pizza cutter", "Scissors"]}` (curl: `curl -i -H "@auth.txt" -d "@all_tools.json" https://quickpizza.grafana.com/api/pizza`)
- Expected result: status 400 with a JSON error message that says no pizza can satisfy the restrictions
- Actual result: status `500 Internal Server Error`, `Content-Length: 0`, empty body
- Severity: Medium. The request is uncommon and nothing is corrupted, but the server fails on valid input, and the client gets no message to show the user, so an app that calls `res.json()` on the answer crashes.

## Part B
1. A real server can show failures that a stub hides: (a) integration failures between the parts, for example the web server, the code and the database disagreeing on the format of a field, or a 500 from deep inside the server, as in Defect 1; (b) environment and network failures, such as the load balancer sending requests to different servers (Step 0.12), wrong configuration, or a wrong status code or header from the real framework. Unit tests with stubs are still worth writing because they are fast and deterministic, do not depend on the network or on shared data, and point straight to the function that is wrong, so edge cases can be tested cheaply on every change.
2. The public token is shared by everyone, so another student can change or delete those ratings while my test runs, and my tests would change data that belongs to others. A new user per test gives every test its own data, so the tests are independent and repeatable and pass in any order. In Project 2 I will make each test create its own customer, cart, order or booking with a unique name (for example with `uuid`), use only the data my group created, and delete it in a fixture after the test.
3. QuickPizza runs on several servers behind a load balancer, and each server keeps its own users. The session keeps the AWSALB cookie that the load balancer sets, so every request after the first goes to the same server, and a user created by one request can log in with the next. In my three runs of Step 0.12 without a session, the test passed once and failed twice at login, so the test was flaky.
4. The block "all three tools are excluded" revealed the defect. A 500 with an empty body tells the calling app nothing: it cannot tell a server crash from a bad request, it cannot show the user a reason, and code that parses the body as JSON fails. A 400 with a message says that the client's input is the problem and what to change. The test stays as xfail so that the defect stays visible in every run and in the report while the rest of the suite stays green, and with `strict=True` the run fails as soon as the defect is fixed, which reminds us to remove the mark and keep the test as a regression test.
5. Base choice coverage needs 1 + (3−1) + (4−1) + (2−1) + (3−1) = 1 + 2 + 3 + 1 + 2 = 9 tests: one base test, then one test for every non-base block. All combinations coverage needs 3 × 4 × 2 × 3 = 72 tests, one for every combination of blocks.
6. Read gave 404, change gave 400 and delete gave 400. I would expect 403 Forbidden (the rating exists but belongs to someone else), or 404 Not Found for all three (which hides that the rating exists, also a safe choice). The access control itself works, because every attempt was refused and the rating stayed unchanged, so it is not a security defect. But 400 Bad Request is the wrong code, since the request itself is well formed, and the codes are inconsistent between read (404) and change/delete (400). I count it as a minor defect in the error handling of the API, not in its security.
7. With the made-up token `0000000000000000` the request answers `200 OK` with a list of ratings that I never created, instead of 401. Any 16-character token is accepted, so QuickPizza does not check that the token belongs to a logged-in user. On a demo site this is by design, but on a real system it is a serious security defect (broken authentication): a stranger could make up tokens and read, and possibly change or delete, other people's data without logging in.
8. An API test checks the exact status codes, headers and JSON fields of each response, and the rules that the server must enforce even when someone bypasses the web page (for example a rating of 6 stars, or another user's rating), faster and more reliably than a browser test. Only a test through the web pages can check what the user actually sees and does: the layout, the text and buttons on the screen, the JavaScript in the browser, and whether the page shows the right message when the API answers with an error.
